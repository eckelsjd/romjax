## Objective
Implement a YAML-driven `GraphTrain` routine that optimizes edge parameters in a `FunctionGraph` using persisted graph datasets and configurable graph-based loss terms. The implementation should treat [demo/train.yml](/home/eckel/project-romjax/romjax/demo/train.yml) as the primary contract, mirror the ergonomics of [demo/gen_data.yml](/home/eckel/project-romjax/romjax/demo/gen_data.yml) and `DataGeneration`, and provide focused tests for config validation, dataset loading, loss construction, parameter initialization, and routine execution.

- [ ] Avoid mutating graph/model state inside the differentiated step. Runtime parameter application should be explicit and functional.
- [ ] Reuse existing utilities where they already fit the design: `FunctionGraph.reconstruction_error`, tree operator registries, `gen_keys`/distribution helpers, `load_h5`, `save_h5`, and the existing low-level `train(...)` loop.

- [ ] Maintain deterministic behavior for dataset ordering, shuffling, initialization, and validation so runs are reproducible for paper-facing workflows.

## Key challenges and sharp points
The main sharp point is translating the rich but still compact YAML contract in `demo/train.yml` into a clean public API without letting the routine dissolve into arbitrary callables. `GraphLoss`, `GraphDataLoader`, and `GraphInitParams` should be explicit validated abstractions, not loose dictionaries.

The second sharp point is parameter application. The training routine needs to optimize edge-specific parameters while preserving shared references such as `residual transform: coordinate transform`, and it should do that in a functional way that does not mutate graph objects inside a differentiated step.

The third sharp point is dataset semantics. `DataGeneration` persists data grouped by sampled edge and nested input/output samples, while training loss terms are grouped by graph path and optional regularizers. The dataloader and loss API should make that mapping explicit and deterministic rather than guessing at node or file semantics.

The existing [src/romjax/train.py](/home/eckel/project-romjax/romjax/src/romjax/train.py) loop is useful but not yet aligned with the desired public config. Right now there is no real `GraphTrain`, no public `GraphDataLoader`, no `GraphLoss` aggregate matching `demo/train.yml`, and no `GraphInitParams` object. The later implementation pass should be willing to reshape the module if that leads to a cleaner user-facing routine.

## More context (optional)
The requested design is very close to the existing `DataGeneration` workflow: one YAML-backed routine object owns a root directory, loads a graph from file, validates the user configuration, and then runs a reproducible file-based pipeline. The main difference is that training combines several runtime concepts at once: loading saved samples, constructing batched graph losses, initializing parameter pytrees, and driving an optimizer.

A good first implementation target is the exact `demo/train.yml` story:
- a graph loaded from `demo/poisson_graph.yml`
- one training loader and one validation loader that read the generated dataset tree
- two reconstruction terms tied to the `poisson` dataset edge and graph paths like `[coordinate transform]` and `[residual transform]`
- one regularization term with `dataset: null`
- an optax optimizer resolved through `ThirdPartyType`
- initialized parameters for named edges, including shared references
- deterministic stopping, saving, and optional validation evaluation

If that path works cleanly on a toy graph and through targeted tests, the resulting abstractions should also scale to the Poisson demo and later paper experiments without revisiting the config model again.
