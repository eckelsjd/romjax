# AGENTS.md

## Overview

This repository contains a Python library for **computational science research workflows**, including simulation, PDE solvers, reduced-order modeling, machine learning, optimization, and post-processing.

The codebase prioritizes:

* **Clarity over cleverness**
* **Reproducibility of scientific results**
* **Composable abstractions**
* **High numerical performance**
* **Portability across CPU/GPU environments**

Agents and contributors should aim to produce **clean, readable, well-typed Python code** that integrates smoothly into scientific workflows.

## Development Philosophy

This project follows several guiding principles.

### 1. Readability First

Code should be understandable by a scientist reading it for the first time.

Prefer:

* descriptive but concise variable names
* explicit logic
* simple abstractions
* clear data flow

Avoid:

* overly clever one-liners
* unnecessary metaprogramming
* deep inheritance hierarchies

### 2. Reproducible Science

Scientific workflows must be reproducible.

Therefore:

* configuration is stored in **YAML files**
* schemas are validated with **Pydantic**
* randomness must be **explicitly seeded**
* experiments must be **fully configurable**

### 3. Functional Core, Imperative Shell

The library favors **pure functions and explicit data flow**.

Core computational routines should:

* avoid side effects
* operate on explicit inputs
* return explicit outputs

I/O, logging, and orchestration should live at the edges of the system.

### 4. Performance Matters

Scientific computing often requires high performance.

Performance priorities:

1. **Vectorized operations**
2. **JAX transformations (jit, vmap, grad)**
3. Avoid Python loops when possible
4. Minimize unnecessary allocations

However:

> Never sacrifice clarity unless profiling demonstrates a need.

## Technology Stack

The project uses the following software stack.

### Core Numerical Computing

* **NumPy** — baseline numerical array operations
* **JAX** — accelerated and differentiable computation

Guidelines:

* Prefer **JAX-compatible code** when gradients or GPU execution may be required
* Write functions that work with any **ArrayLike** inputs, including `numpy.ndarray` and `jax.Array` but also built-ins like `list` and `float`

### Configuration and Validation

* **YAML** — experiment configuration
* **Pydantic** — schema validation and type enforcement

Configuration files should:

* describe experiments
* define model parameters
* define solver settings
* specify I/O paths
* point to callables with `!!python/name` tags
* point to classes with custom `module.path` tags

Example:

```yaml
solver: !model:romtools.solvers.poisson.Poisson2D
  forcing: !!python/name:romtools.solvers.poisson.gaussian_forcing
  tolerance: 1e-6
  max_iterations: 1000
```

### Visualization and Post-Processing

* **Matplotlib** — plotting and visualization
* **HDF5** — data persistence

Plots should:

* be generated by **separate analysis scripts**
* never be embedded inside core computational code

## Project Structure

The project follows this layout:

```
romtools/
├── .venv — virtual environment managed by `uv`
├── src/romtools — python library API
├── scripts/ — Standalone scripts for experiments and analysis
├── tests/ — Unit and integration tests
│   Unit and integration tests
```

Guidelines:

* **Core library code lives in `src/`**
* Scripts are mainly just for temporary testing
* Add unit tests for all major changes in the API
* Run tests with `uv run pytest`
* Always work inside the `uv` virtual environment

## Coding Standards

### Python Version

Target:

```
Python ≥ 3.14
```

### Formatting

Follow **PEP 8** with a line-length of `120 characters`.
See `romtools.dataloader.py` for a good example.
Use in-line comments to add clarity where needed.

### Type Hints

All public functions should include **type annotations**.

Example:

```python
def solve_poisson(
    kappa: Array,
    source: Array,
    boundary_conditions: BoundaryConditions,
) -> Array:
    ...
```

Guidelines:

* Prefer **explicit types**
* Avoid `Any` unless unavoidable
* Use **protocols or dataclasses** for structured inputs
* Use modern Python typing standards (https://mypy.readthedocs.io/en/stable/cheat_sheet_py3.html)
* Prefer built-in types, for example `dict` instead of `Dict`
* Use the convention `type1 | type2` instead of the older `Union[type1, type2]`
* Use "wider" types where possible, for example `Sequence[int]` instead of `list[int]`
* Prefer newer conventions over backwards compatibility, for example `type MyType = ...` instead of `MyType = ...`
* Use pydantic validation where possible, but don't overburden functions that are intended for use in the `jax` pipeline

### Docstrings

Use **Sphinx-style docstrings**. Use latex equations that can be rendered by mathjax.
You may also use admonitions compatible with `mkdocs` for emphasis.

Example:

```python
def compute_residual(u: Array, f: Array) -> Array:
    """
    Compute the PDE residual.

        $\nabla\cdot(\kappa\nabla\phi)=0$
    
    !!! Note "Finite-differences"
        We use central differencing everywhere unless otherwise noted.

    :param u: solution field
    :param f: forcing term
    :return: residual field
    """
```

### JAX Coding Guidelines

When writing JAX-compatible code:

Prefer:

```
jax.numpy as jnp
```

instead of NumPy when inside differentiable code.

Example:

```python
import jax.numpy as jnp
```

Use transformations appropriately:

* `jax.jit` for heavy numerical kernels
* `jax.vmap` for batched operations
* `jax.grad` for differentiation

Avoid:

* Python side effects
* mutation inside jitted functions
* non-JAX compatible libraries

### Configuration Pattern

Configurations should be:

1. **Defined in Pydantic models**
2. **Loaded from YAML**
3. **Validated before use**

Example pattern:

```python
class SolverConfig(BaseModel):
    tolerance: float
    max_iterations: int
```

Load workflow:

```
YAML → Pydantic model → runtime objects
```

## Testing
Run all tests with `uv run pytest`. Read all output and correct all failing tests before continuing.

## Agent Behavior Guidelines

When modifying this repository, agents should:

1. Preserve existing architecture
2. Prefer small, composable functions
3. Avoid unnecessary dependencies
4. Add tests when introducing new functionality
5. Add docstrings to all new functions and classes

Agents should **not**:

* introduce hidden global state
* introduce heavy frameworks
* break JAX compatibility
